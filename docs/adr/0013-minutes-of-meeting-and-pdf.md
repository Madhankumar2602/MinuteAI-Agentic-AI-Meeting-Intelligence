# ADR 0013 — Minutes of Meeting as the central output: one data model, a stored PDF, audio extracted from video

- **Status:** Accepted
- **Date:** 2026-09-14
- **Milestone:** M7 (core workflow)

## Context

The product's success criterion was clarified: a user provides **meeting notes,
a transcript, audio, or video**, and MinuteAI produces **structured Minutes of
Meeting (MOM)** that can be viewed and downloaded as a **PDF**. RAG and agent
automation are layers on top of that.

A gap analysis of M1–M6 (PROJECT_STATUS) found that the pipeline was mostly
right, but the output stopped at "intelligence records":

- no keywords, speaker contributions, pending items, or next steps;
- no single MOM document and no PDF;
- notes could only be pasted as if they were a transcript;
- the agenda was never shown to the model;
- a video was sent to the transcription model whole.

## Decisions

### 1. Extend the existing extraction; do not add a second LLM call

Prompt `extract-v2` asks the same single structured call for the extra MOM fields:
keywords, speaker contributions, unresolved items, and next steps. The same
deterministic normalisation applies, with new rules for the new fields:

- keywords are de-duplicated case-insensitively and capped;
- unresolved items are evidence-verified like decisions;
- speaker turn and word counts are **counted from the transcript's `Name:`
  lines**, never estimated by the model, and joined to its contribution summaries.

A second "MOM writer" call would double cost and latency, and create a second
source of truth that could contradict the first. Because the prompt version
changed, stored v1 results are no longer current, and re-processing fills in the
new fields.

The fields are stored as JSONB on `summaries` (migration `0006`), following the
`key_points` precedent: small, ordered, and always read whole.

### 2. Notes are a distinct input kind

`PUT /transcript` accepts `kind: "notes"` (`transcripts.source = 'notes'`). The
prompt states `INPUT TYPE: MEETING NOTES`. Notes skip speaker counting, so a line
like `Agenda: …` is not treated as a person. Notes are human input, so, like a
typed transcript, they are never overwritten by a recording's transcription.

The meeting description is sent as a fenced `AGENDA` block. The model is told to
use it for context, but to extract only what the input shows actually happened.
Fence markers inside any untrusted text are neutralised (`<<<` → `‹‹‹`), so an
agenda cannot fake the end of the input block (tested).

### 3. One `MinutesOfMeeting` model, assembled from stored records

`services/mom/builder.py` builds the MOM from the meeting, transcript, recording,
summary, participants, decisions, and action items **at read time**. The same
object feeds `GET /meetings/{id}/mom`, the web Minutes tab, and the PDF.

- A user's corrections (a task marked done, a decision resolved) appear in the
  next view and the next PDF automatically.
- The web page and the PDF cannot disagree.
- "Next steps" fall back to open action items when none were stated, and the MOM
  marks them as derived.

### 4. Validation is deterministic code, not the project's AI agent

The validation stage of the core flow (called "agentic validation" in the original
workflow sketch) is `review_minutes()`: rule-based validation logic, a pure function
that raises the flags a careful minute-taker would check before sending:

- an open action item with no owner;
- an open action item with no deadline, or wording that could not be resolved to
  a date;
- evidence not found in the input;
- unnamed speakers (`Speaker 2`);
- a transcript edited since extraction.

This is **rule-based validation logic**, not an AI agent, and is never described
as one. It is predictable, testable, and free.

### 5. PDF: ReportLab, embedded DejaVu fonts, content-addressed storage

| Option | Verdict |
|---|---|
| **ReportLab (chosen)** | Pure-Python wheels, precise tables and pagination, no system dependencies on Windows, Linux containers, or Lambda |
| WeasyPrint (HTML → PDF) | Nicer templating, but needs Pango/GTK system libraries; painful on Windows and in Lambda |
| Browser print (client-side) | The PDF would not exist server-side, so it could not be stored or regenerated by the job |

- **Fonts.** DejaVu Sans is bundled (free licence, in `services/mom/fonts/`). The
  PDF base fonts cover only Latin-1, so "Łukasz", "Ζωή", "₹", and "€" would
  otherwise print as boxes (tested).
- **Escaping.** ReportLab paragraphs interpret XML-like markup. All user and
  model text is escaped, so `<font size=40>` in a transcript prints literally
  (tested; the test fails if escaping is removed).
- **Layout.** Cover block (title, date/time, participants, input, topics),
  agenda, then numbered sections: summary, discussion points, speakers,
  decisions, action items (owner, deadline with the original wording, status),
  pending items, next steps, items needing review, and source & transcript
  reference with an evidence appendix. Every page has a "Page n of N" footer.
- **Storage.** The key is `users/{u}/meetings/{m}/mom/{fingerprint}.pdf`, where the
  fingerprint is SHA-256 of the MOM JSON plus the renderer version. The same
  minutes reuse the stored PDF; changed minutes produce a new one, and older ones
  are deleted after the upload succeeds. Deleting the meeting's prefix removes the
  PDFs with everything else.
- **When.** The processing job renders the PDF as its last stage (event
  `mom_pdf_generated`). That stage is non-fatal: the minutes are already
  committed, so a storage hiccup must not fail the meeting or trigger another LLM
  call. `POST /mom/pdf` renders on demand either way.
- **Delivery.** Presigned GET links carry a signed `Content-Disposition`
  (`inline` to view, `attachment` to download, RFC 5987 filename). The web app
  shows the PDF in an in-app preview dialog. Opening a new window from script
  after a request was **blocked by the browser in live testing**, so "Open in new
  tab" and "Download" are ordinary links.

### 6. Extract the audio track from video locally (PyAV)

Video is decoded with PyAV (FFmpeg bundled in its wheels) to 16 kHz mono Opus at
32 kb/s before transcription.

- **Size.** The live test video went from 1.9 MB to 457 KB. Real screen
  recordings shrink far more, since video dominates their size.
- **Privacy.** Slides, faces, and shared screens are never sent to the provider.
- **Accurate duration.** Counted from decoded samples: 154 s, matching the WAV
  header exactly.
- **No audio track.** A video without sound fails permanently with
  `no_audio_track`, before any model call.

## Consequences

- New dependencies: `reportlab`, `av`, and the bundled fonts (~2 MB).
- Rendering a 3-page MOM takes tens of milliseconds; a reused PDF answers in about
  40 ms.
- DejaVu does not cover CJK or Indic scripts. Text in those scripts would render
  as boxes; adding Noto fonts would fix it at a few MB per script.
- Speaker counts depend on `Name:` lines. Transcripts without speaker labels get
  contributions from the model but no counts.
- Transcription mistakes flow into the minutes. In live testing the model spelt
  "Meera" as "Mira" and credited one diagnosis to the wrong speaker. The review
  flags cannot detect this; the transcript tab and evidence appendix let a person
  check.
